# Relationship CRUD Exposure — Design Spec

Date: 2026-09-09
Status: Approved for implementation planning
Extends: `docs/superpowers/specs/2026-09-08-erd-cli-design.md`,
`docs/superpowers/specs/2026-09-09-modular-services-design.md`

## 1. Motivation

An ERD can declare relationships (`many-to-one`, `one-to-one`, `one-to-many`,
`many-to-many`) between entities, and `database/models.py` correctly wires
them up — FK columns, SQLAlchemy `relationship()`, association tables for
many-to-many. This was verified to work at the DB layer for all four
cardinalities, including the "association object" pattern (three ordinary
entities, two `many-to-one` relationships, e.g. `Student`/`Course`/
`Enrollment`), via live SQLite round-trips.

But none of it is reachable through the generated HTTP API. `translate.py`'s
`crud_entities` — what `module_schemas.py.jinja`/`module_service.py.jinja`/
`module_routes.py.jinja` render from — only carries `entity.fields`, never
`entity.relationships`. So every generated `Create`/`Update`/`Response`
schema is blind to relationships regardless of cardinality: you cannot set a
`Post`'s `category` through the API, you cannot create an `Enrollment` linked
to a `Student`/`Course` through the API (no `student_id`/`course_id` field
exists anywhere in `EnrollmentCreate`), and a many-to-many's association is
never visible in any response. The database layer is fully wired; the
generated API cannot touch any of it. This spec closes that gap for the two
cases that matter most in practice: FK exposure/validation (the case that's
completely broken today) and read-only many-to-many exposure.

A verified stopgap already exists and keeps working after this ships:
manually re-declaring an FK column as an ordinary field in the ERD (e.g.
`{name: student_id, type: integer}` on `Enrollment`) already produces a
working `student_id` field in the schema today, because `models.py.jinja`
already deduplicates a field that collides with a relationship-derived FK
column. This spec makes that automatic, and adds the validation and
many-to-many pieces the manual workaround still doesn't cover.

## 2. Scope boundary

**In scope:**
- Every `many-to-one`/`one-to-one` relationship, and every `one-to-many`
  relationship *from the FK-owning side's perspective* (see §3 — "owned"
  relationships are defined by which entity holds the FK column, not by
  which cardinality keyword declared it):
  - `<fk_column>` (e.g. `category_id`) added to `Create`, `Update`, and
    `Response` schemas.
  - Explicit existence validation on `create`/`update`: a nonexistent
    referenced id raises a client-facing `400`, not a raw DB error (or,
    on SQLite specifically, silent insertion of a dangling reference —
    SQLite generated by this CLI does not enable `PRAGMA foreign_keys`,
    so today nothing enforces this at all).
  - An optional query-param filter on the owning entity's own `list`
    endpoint (e.g. `GET /posts?category_id=5`), reusing the existing
    paginated list endpoint rather than adding a new route.
- Every `many-to-many` relationship: a read-only `<target_plural>_ids`
  field (e.g. `tag_ids: List[int]`) on `Response` only, populated via
  `selectinload` in the repo layer to avoid N+1 queries on `list`/`get`.

**Explicitly out of scope** (per discussion — may become their own future
items, not designed further here):
- Many-to-many **write** support (setting `tag_ids` via `Create`/`Update`,
  or a future `PUT /posts/{id}/tags` sub-resource endpoint).
- Nested full-object responses (`category: CategoryResponse` instead of
  `category_id: int`) for any cardinality.
- Nested collections on the "one" side of a one-to-many
  (`CategoryResponse.posts: List[PostResponse]`) — the query-param filter
  on the "many" side's own list endpoint covers this need instead, without
  the N+1/pagination problems a nested collection would have.
- Any new ERD YAML syntax. This behavior is automatic for every
  relationship — no per-relationship opt-out/opt-in flag. Nothing today
  gives users field-level generation toggles, and adding one here would be
  scope creep beyond what's needed to close this gap.

## 3. Data flow: `crud_entities` gains relationship data

`translate.py` already computes a full `relationships` list and attaches
each relationship to both `data_models[entity]["relationships"]` (source and
target). `crud_entities` (built separately, a few lines later in the same
function) gets two new derived keys per entity, computed from that same
per-entity relationship list — no new parsing of the ERD:

```python
{
    # ... existing crud_entities keys unchanged ...
    "owned_relationships": [
        {
            "attribute": rel["source"]["attribute"] if rel["source"]["model"] == entity.name else rel["target"]["attribute"],
            "fk_column": rel["foreign_key"]["column"],
            "fk_nullable": rel["foreign_key"]["nullable"],
            "target_model": <the OTHER side's model name>,
            "target_snake": _snake_case(<target_model>),
        }
        for rel in <this entity's relationships>
        if rel.get("foreign_key") and rel["foreign_key"]["model"] == entity.name
    ],
    "many_to_many_relationships": [
        {
            "attribute": rel["source"]["attribute"] if rel["source"]["model"] == entity.name else rel["target"]["attribute"],
            "target_model": <the OTHER side's model name>,
            "target_plural_snake": _pluralize(<target_model>),
        }
        for rel in <this entity's relationships>
        if rel["cardinality"] == "many-to-many"
    ],
}
```

(`<the OTHER side's model name>` in both blocks above: whichever of
`rel["source"]["model"]`/`rel["target"]["model"]` is not `entity.name`.)

**Important generalization:** "owned" is defined by
`foreign_key.model == entity.name`, not by which cardinality keyword the
YAML used to declare it. A `one-to-many` declared from the parent side
(`Category` declares `cardinality: one-to-many, target: Post`) and the
logically-equivalent `many-to-one` declared from the child side (`Post`
declares `cardinality: many-to-one, target: Category`) both normalize to
the same `foreign_key.model == "Post"` in `translate.py` today — so both
must produce an identical `Post.category_id` in the generated schema. This
is exactly the "association object" pattern from the user's original
question (`Enrollment` owns FKs to both `Student` and `Course`, entirely
via `many-to-one` declarations) — no special-casing needed, it falls out of
the general rule.

## 4. Schema generation (`module_schemas.py.jinja`)

For each entry in `owned_relationships`:
- `Create`: `{{ fk_column }}: {% if fk_nullable %}Optional[int] = None{% else %}int{% endif %}`
- `Update`: `{{ fk_column }}: Optional[int] = None` — always optional,
  matching the existing convention that every `Update` field is optional
  regardless of the underlying column's nullability (a partial/PATCH
  update never requires a field).
- `Response`: same shape as `Create`'s annotation (required int, or
  `Optional[int]`, mirroring the field's actual nullability) — added
  alongside the entity's own fields, not nested.

For each entry in `many_to_many_relationships`, `Response` only gets
`{{ target_plural_snake }}_ids: List[int]`. Since a plain
`class Config: from_attributes = True` can't rename+transform `tags`
(a list of ORM `Tag` objects) into `tag_ids` (a list of `int`) on its own,
the `Response` class gets a Pydantic v2 `model_validator(mode="before")`
that, given the raw ORM object, reads `getattr(obj, "<attribute>")` and
maps it to `<target_plural_snake>_ids = [t.id for t in ...]` before the
rest of the model validates normally. `Create`/`Update` get nothing for
many-to-many relationships (read-only, per §2).

## 5. Service layer: FK existence validation

For each `owned_relationships` entry, `create_<entity>`/`update_<entity>`
in the module's service class gets an explicit check before delegating to
`repo`, calling the shared repo layer's existing `get_<target_snake>_by_id`
(already generated for every entity, regardless of which module it lives
in — `repo.py` is one shared file imported by every module's service, so
this works identically for same-module and cross-module relationships,
e.g. `shophub_mini.yml`'s `Order` in `ordering` validating against
`Product` in `catalog`):

```python
def create_post(self, db: Session, data: dict) -> Post:
    if data.get("category_id") is not None and repo.get_category_by_id(db, data["category_id"]) is None:
        raise ValueError(f"Category {data['category_id']} not found")
    return repo.create_post(db, data)
```

Same shape for `update_post`, only checking when `category_id` is present
in the partial update payload.

`module_routes.py.jinja`'s `create`/`update` handlers get a
`try/except ValueError` around the service call, mapping it to
`HTTPException(status_code=400, detail=str(exc))` — extending the pattern
already established in `auth/routes.py`'s `register`/`login` (`ValueError`
→ `400`) to the generic CRUD routes, which don't currently catch anything
service-side.

A `None` `category_id` on a nullable FK is never validated (nothing to
check). A missing required (`fk_nullable: false`) FK on `Create` is
already rejected by Pydantic itself (`422`) before the service method
ever runs — the service-level check only needs to cover "present but
wrong", not "missing".

## 6. Read side: query-param filter + N+1 avoidance

**Query-param filter.** For each `owned_relationships` entry, the entity's
own `list_<x>_route` gains an optional query parameter:

```python
def list_post_route(
    skip: int = Query(0, ge=0),
    limit: int = Query(100, ge=1, le=500),
    category_id: Optional[int] = Query(None),
    ...
) -> List[PostResponse]:
    return service.list_posts(db, skip=skip, limit=limit, category_id=category_id)
```

threaded through `<Module>Service.list_<x>` and `repo.get_all_<plural>`,
which adds `.filter(Post.category_id == category_id)` only when the param
is given. This directly answers "show me posts in category X" (raised
during design) without a nested collection on `CategoryResponse` and its
N+1/pagination problems.

**N+1 avoidance for many-to-many.** `repo.get_all_<plural>`/
`get_<x>_by_id` add `.options(selectinload(<Model>.<m2m_attribute>))` for
every many-to-many relationship the model has. `selectinload` issues one
extra query total for the whole result set (not one per row), so
`GET /posts?limit=100` with each post having tags costs exactly 2 queries,
not 101.

## 7. Testing plan

- `translate.py` unit tests: `owned_relationships`/`many_to_many_relationships`
  compute correctly — nullable vs. required FK, correct target model on
  both a `many-to-one`-declared and an equivalent `one-to-many`-declared
  relationship (proving the generalization in §3), many-to-many attribute
  naming.
- Generation-level tests (extending `one_to_one.yml`/`overrides.yml`, plus
  a new many-to-many fixture, since no full-pipeline many-to-many
  generation test exists today): rendered `schemas.py`/`service.py`/
  `routes.py` contain the expected fields/validation/query-param, and
  still `ast.parse`/byte-compile.
- **Real HTTP+DB round-trip** (matching the existing convention in
  `test_generated_project_runtime.py`, the strongest signal this codebase
  uses): `POST` a `Post` with a valid `category_id` → `201` with
  `category_id` in the response body; `POST` with a nonexistent
  `category_id` → `400`; `GET /posts?category_id=X` → only matching posts;
  `GET /posts` against tagged posts → `tag_ids` present and correct. A
  query-count assertion (e.g. via SQLAlchemy's event hooks or `echo`
  capture) around the many-to-many list case, to catch a future N+1
  regression if `selectinload` is ever dropped from a template edit.

## 8. Non-goals / follow-ups

Explicitly parked, not designed further here (see the repo backlog):
- Many-to-many write support.
- Nested full-object / nested-collection responses.
- Any of this interacting with row-level access control (not designed yet)
  or async support (not designed yet) — this spec's service-layer
  validation and repo-layer query changes are written sync, matching the
  rest of the codebase today, and will need revisiting whenever async
  support is designed.
