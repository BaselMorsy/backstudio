# Fixing the 4 issues found while building the example showcases — Design

## 1. Motivation

Building three new production-shaped example ERDs (`ecommerce.yml`,
`multi_tenant_saas.yml`, `personal_finance.yml`) and testing them end to end
surfaced four real findings, documented in `examples/ISSUES.md` and left
deliberately unfixed at the time for review. This spec covers fixing all
four: one genuine code-generation bug, two RLS capability gaps, and one
documentation gap.

## 2. Scope boundary

In scope: the four issues named in `examples/ISSUES.md`, and nothing else.
Two of the four (RLS read scope, header-RLS bypass) are real capability
additions to the RLS mechanism, decided via two explicit choices already
made: "public read" means *any authenticated user*, not a fully open
unauthenticated endpoint; and header-based RLS *will* support
`bypass_roles`, resolved via the caller's RBAC role membership (not via the
header itself, which carries no role information).

Out of scope: any other RLS extension not named in the four issues; any
change to the many-to-many-writes-stay-read-only limitation (not one of the
four issues — it was confirmed as already-intentional, not a new finding);
any change to `endpoints.base_path`'s actual behavior (issue #4 is a
documentation gap, not a behavior change).

## 3. Issue 1 — Unescaped free-text ERD fields break generated Python source

### 3.1 Root cause

Confirmed concretely: `app/templates/Python/server.py.jinja` embeds
`project.description` directly inside a double-quoted Python string literal
with no escaping (`description="{{ project.description or '...' }}"`). A
literal `"` in the value produces invalid Python. The same raw-interpolation
pattern (`"{{ project.name }}"` inside a double-quoted literal, or inside a
triple-quoted module docstring) recurs across essentially every template in
`app/templates/Python/` for `project.name`, and specifically for
`project.description` in `server.py.jinja`.

### 3.2 Fix

Use Jinja's `tojson` filter everywhere a free-text ERD field lands inside a
Python string literal. `tojson` produces a JSON string literal (proper
backslash/quote escaping, unicode-safe) that is also valid Python syntax for
a plain string value — `{{ (project.description or 'Generated by BackStudio')
| tojson }}` instead of a manually-quoted literal. This is the standard,
already-idiomatic-in-this-codebase way to safely embed a value inside
generated source (the same technique this repo already uses in
`server.py.jinja`'s auth-routes for embedding role lists:
`{{ project.rbac_roles|tojson }}`).

### 3.3 Full audit required, not just the two known spots

The plan must systematically grep every file under `app/templates/Python/`
for every place `project.name`, `project.description`, or any other
free-text ERD field (entity/field descriptions if any exist in the schema —
verify against `app/erd/schema.py`) is interpolated inside a string literal
— both single-line double-quoted literals (the genuinely broken case) and
triple-quoted module docstrings (lower risk, but a value ending in a quote
character or containing `"""` would still break one; fix these too for
correctness even though they're not the reproduced failure). Do not assume
the list already enumerated in `examples/ISSUES.md` is exhaustive — it was
compiled by targeted grep during the examples work, not a full audit.

### 3.4 Non-goal

No change to what characters are *permitted* in `project.name`/`description`
at the schema-validation level (no new regex restricting them) — the fix is
purely "these values render safely into generated Python regardless of
their content," not "restrict what values are allowed."

## 4. Issue 2 — RLS: public read, owner-only write

### 4.1 New schema field

`RLSSpec` gains one new field:

```python
read_scope: Literal["owner", "any_authenticated"] = "owner"
```

Default `"owner"` preserves today's behavior exactly (reads filtered to the
resolved owner, identical to every existing RLS-using ERD/fixture/example —
zero behavior change for anything that doesn't opt in). `"any_authenticated"`
means: `list`/`read` actions are **not** filtered by owner — any caller who
passes the entity's normal RBAC gating (which, per existing rules, already
requires `auth.enabled: true` whenever RLS is in play, so "authenticated"
is already guaranteed) sees every row, not just their own.

`create`/`update`/`delete` are **always** owner-filtered/owner-stamped
regardless of `read_scope` — this field only loosens the read path.
`read_scope: any_authenticated` is independent of `bypass_roles`, which
keeps its existing, already-precedented scope exactly as-is: `create`
always stamps the caller's own id no matter what (confirmed in the current
`module_routes.py.jinja`, which documents this exact asymmetry in its own
comment: "create always stamps the caller's own id... a NULL owner is
invisible to every non-bypass caller forever"); `bypass_roles` bypasses
filtering on `list`/`read`/`update`/`delete` only. `read_scope:
any_authenticated` simply makes that same "list`/`read` see everything"
outcome apply to *every* caller instead of only bypass-role callers —
`update`/`delete` stay owner-filtered for non-bypass callers regardless of
`read_scope`.

### 4.2 Mechanism (grounded in the current, real template code)

The repo layer (`app/templates/Python/database/repo.py.jinja`) already
implements the exact mechanism needed, unconditionally, for every RLS'd
entity's read functions:

```python
if owner_id is not None:
    query = query.filter(Model.owner_fk_column == owner_id)
```

i.e. passing `owner_id=None` already means "no filter" — this is the *same*
mechanism `bypass_roles` already uses for `auth_user`-identity entities
(`owner_id = None if <caller has a bypass role> else current_user.id`, in
`module_routes.py.jinja`). **No repo-layer change is needed.** The fix is
entirely in the route layer (`module_routes.py.jinja`): for `list`/`read`
actions on an entity with `rls.read_scope == 'any_authenticated'`, pass
`owner_id=None` unconditionally, instead of computing it from the current
user/bypass-role logic. `create`/`update`/`delete` keep computing and
passing a real `owner_id` exactly as today, uninfluenced by `read_scope`.

## 5. Issue 3 — `bypass_roles` for header-based RLS

### 5.1 What changes

Currently, `app/erd/loader.py`'s `_validate_rls` hard-rejects
`bypass_roles` whenever `identity_source.type == 'header'`, with this exact
message (to be removed):

> `rls.bypass_roles has no effect when identity_source.type is 'header' —
> the header identity source resolves ownership purely from the request
> header and never reads any role information, so there is nothing for a
> bypass role to plug into. Remove bypass_roles, or switch to
> identity_source.type: auth_user.`

This rejection is removed. `bypass_roles` on a header-identity entity now
means: a caller whose RBAC roles (from their JWT — always available,
because `bypass_roles` already independently requires `rbac.enabled: true`,
which already requires `auth.enabled: true`) intersect `bypass_roles`
bypasses the header-based filter entirely, mirroring the existing
`auth_user` bypass semantics exactly. The two other existing validation
rules for `bypass_roles` (requires `rbac.enabled: true`; every listed role
must be declared in `rbac.roles`) are unchanged and apply identically
regardless of identity source — only the header-specific hard rejection
goes away.

### 5.2 Mechanism (grounded in the current, real template code)

Today, a header-identity route's `Header(...)` parameter is unconditionally
required (`rls_owner_header: int = Header(..., alias="X-Tenant-Id")`), and
the route body has no `current_user` parameter at all for header-identity
entities — RBAC gating happens at the decorator level
(`Depends(require_roles(...))`), never exposing the caller's own roles to
the route body, because until now nothing inside a header-identity route
needed to know who the caller was.

The fix, scoped to `entity.rls.identity_source.type == 'header' and
entity.rls.bypass_roles` (the new case): the route also depends on
`current_user` (the same dependency `auth_user`-identity routes already
use), and the header parameter becomes optional
(`Header(None, alias=...)`) rather than required. Resulting logic, mirroring
the existing `auth_user` bypass line:

- If `current_user`'s roles intersect `bypass_roles`: `owner_id = None`
  (skip filtering) for `list`/`read`/`update`/`delete` — the header is not
  required for a bypass-role caller on these actions.
- Otherwise: the header **is** required (`Header(..., alias=...)` semantics
  preserved for non-bypass callers — a missing header still 422s exactly as
  today), and `owner_id = rls_owner_header` as today.
- **`create` is a deliberate exception**: the header remains **required
  even for bypass-role callers** — a newly-created row needs a concrete
  owner/tenant value stamped on it; there is no "ownerless" row concept.
  A bypass-role caller creating a row for a specific tenant still supplies
  that tenant's `X-Tenant-Id` explicitly (they're creating *for* that
  tenant, not bypassing anything about the write itself — only reads and
  the "find this row to update/delete it" lookup are what bypass concerns).

This exact create-vs-other-actions asymmetry needs to be implemented
precisely — the plan must show the literal before/after Jinja for each of
the five action routes (create/list/read/update/delete) on a header-identity
entity, not just describe it in prose.

### 5.3 Non-goal

No change to `identity_source.type: header`'s behavior when `bypass_roles`
is *not* set — that path is untouched, still requires the header
unconditionally, exactly as today.

## 6. Issue 4 — Document that module/service names are not URL prefixes

### 6.1 Fix

Pure documentation. Two edits:

- `docs-site/erd-reference/fields.md`'s `endpoints.base_path` row/section:
  state explicitly, next to the existing "Overrides the generated route
  prefix" description, what the *default* (no `base_path` set) actually is
  — routes are mounted directly at the API root with no module/service-name
  prefix at all (only the auth module's routes get a prefix, `/auth` by
  default, configurable via `auth_module_name`).
- `docs-site/architecture/templates.md`: add a short, explicit note in the
  section describing the `modules`-loop / route generation, stating the
  same fact plainly, so a reader building a mental model of the generated
  project's URL layout doesn't make the same wrong assumption (module-name
  prefixing, by analogy with the auth module's own prefix) that produced
  this finding in the first place.

### 6.2 Non-goal

No change to the actual mounting behavior — `endpoints.base_path` already
provides an escape hatch for anyone who wants a namespaced prefix; this
issue is purely that the *default* (no prefix) was never stated plainly.

## 7. Testing plan

- **Issue 1**: a new fixture ERD with `project.description` (and
  `project.name`, if schema constraints allow testing it too — check
  `ProjectMeta.name`'s validation) containing a literal `"`, a backslash,
  and a non-ASCII character; generate it; `python -m compileall` every
  generated `.py` file; assert on the literal rendered content of the fixed
  line(s) to prove the escaping is real, not just "happens not to crash on
  this one input."
- **Issue 2**: extend an existing RLS fixture (or add a new one) with
  `read_scope: any_authenticated` on one entity; a real HTTP round-trip
  test proving: user A creates a row; user B (different identity, no
  bypass role) can `GET`/`list` and see user A's row (the new behavior);
  user B attempting `PUT`/`DELETE` on user A's row still gets the existing
  owner-filtered "not found" behavor (unchanged, still owner-only for
  writes); a sibling entity in the same fixture using the *default*
  `read_scope: owner` continues to filter reads exactly as today (proves
  the default is unchanged, not just "the new enum value works").
- **Issue 3**: extend `rls_header_owned_with_rbac.yml` (or a new fixture)
  with `bypass_roles` on the header-identity entity; a real HTTP round-trip
  test proving: a non-bypass caller still requires the header (missing
  header still 422s, wrong header still filters to zero rows, matching
  today); a bypass-role caller can `list`/`read`/`update`/`delete` **without**
  supplying the header at all, seeing every tenant's rows; a bypass-role
  caller attempting `create` **without** the header still fails (the
  create-is-different asymmetry from 5.2, this must have its own explicit
  test — it is the one place bypass does *not* fully apply); a bypass-role
  caller supplying the header on `create` succeeds and stamps the given
  tenant, not some default.
- **Issue 4**: no test — verify the new doc prose is accurate against the
  real current template code one more time at review time (this plan's own
  spec-writing already re-verified it once).
- Full suite must stay green throughout (currently 253 passed); every new
  test is additive.

## 8. Non-goals

- No change to the many-to-many-writes-stay-read-only limitation (a
  different, already-intentional non-goal, not one of the four issues).
- No new RLS identity source types.
- No change to how `bypass_roles` behaves for `auth_user`-identity
  entities — that mechanism is already correct and is the pattern issues
  2 and 3 both extend, not something being altered.
- No retroactive change to any existing fixture/example ERD's behavior —
  every fix here is either purely additive (new opt-in field) or purely
  corrective with no default-behavior change (issue 1's escaping, issue
  4's docs).
