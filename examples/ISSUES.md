# Issues found while building and testing the new examples

Written while designing `ecommerce.yml`, `multi_tenant_saas.yml`, and
`personal_finance.yml` and testing all three (plus the existing `blog.yml`)
end to end via real HTTP-shaped round trips against the actual generated
FastAPI apps. Nothing here has been fixed — per instructions, this is a
findings list for review, not a change log. Generated projects and HTML
diagrams for all four examples are kept under `workspace/` for inspection
(see the bottom of this file for exactly what's there and how it was
verified).

## 1. Bug: unescaped free-text ERD fields break generated Python source

**Severity: real, concrete, reproducible.**

`app/templates/Python/server.py.jinja` (and several other templates)
interpolate `project.description` and `project.name` directly inside a
double-quoted Python string literal with no escaping:

```jinja
description="{{ project.description or 'Generated by BackStudio' }}",
```

If the value contains a literal `"` character, the generated `server.py` is
**not valid Python** — the file fails to even import. Minimal reproduction
(not part of the committed examples, run standalone to confirm):

```yaml
project:
  name: TestApp
  description: This has a "quoted phrase" in it
```

```
$ backstudio generate quote_test.yml --output-dir /tmp/x
$ python -m compileall /tmp/x/TestApp
*** Error compiling '.../TestApp/server.py'...
  File ".../TestApp/server.py", line 22
    description="This has a "quoted phrase" in it",
                ^^^^^^^^^^^^^^^^^^^
SyntaxError: invalid syntax. Perhaps you forgot a comma?
```

I hit this for real (not via the isolated repro) while writing
`personal_finance.yml` — my first draft description used a quoted phrase for
readability and broke the generated project outright.

`project.name` is embedded the same unescaped way in several more files
(`config.py.jinja`'s `APP_NAME: str = "{{ project.name }}"`, `server.py.jinja`'s
`title="{{ project.name }}"`, and the module-level `"""{{ project.name }} - ..."""`
docstring in essentially every template) — I didn't re-run a full generate
cycle to prove `project.name` breaks the same way (I worked around the
`description` case instead of chasing every vector), but it's the identical
code pattern, so it's very likely the same class of bug, just with a smaller
practical blast radius since project names are usually short and less likely
to contain punctuation than free-text descriptions.

**Where this lives**: `app/templates/Python/server.py.jinja` line ~36, and
likely other files with the same `"{{ project.name }}"` / `"{{ ...description... }}"`
pattern — worth a systematic grep across `app/templates/Python/` for every
place a free-text ERD field lands inside a plain double-quoted string literal,
not just the one line I found.

**What I did instead of fixing it**: reworded my example's description to
avoid a literal `"` character (a workaround at the ERD-source level, not a
generator fix).

## 2. Design limitation: RLS can't express "public read, owner-only write"

**Severity: real, but a design question, not a bug.**

Row-level security in this system filters **both reads and writes**
uniformly to the resolved owner's rows for any non-bypass caller (confirmed
against `README.md`'s own description: "scope an entity's reads and writes to
the resolved owner of each row"). There's no way today to express a very
common pattern: content that's **publicly readable** but only **editable by
its owner** — the classic public blog post, public social media post, or
public marketplace listing, where anyone can `GET` it but only the author
can `PUT`/`DELETE` it.

I initially designed the third new example as a "social platform" (public
posts, comments, likes) assuming RLS would give me exactly this — it
doesn't. A `member` role without a bypass role would see **zero** other
users' posts at all, not just be blocked from editing them, which isn't what
a social/content platform needs. I redesigned that example into
`personal_finance.yml` instead — genuinely private per-user data (nobody
else should ever see your transactions, not just be unable to edit them),
which is exactly what this RLS mechanism is built for.

This isn't necessarily wrong as a design choice — private-data RLS is a real
and valuable pattern on its own — but "public read, owner-only write" is
also a very common real-world need that BackStudio currently has no
first-class way to express (a user would have to hand-write that access
control themselves after generation, bypassing RLS entirely for that
entity). Worth a deliberate decision on whether this is in scope for a
future RLS extension (e.g., a `write_only: true` flag on the RLS block) or
stays explicitly out of scope, documented as such.

## 3. Design limitation: header-based RLS can't have a bypass role

**Severity: real, confirmed directly (not inferred) — `backstudio validate` rejects it outright.**

I initially wrote `multi_tenant_saas.yml`'s `Project` entity with:

```yaml
rls:
  identity_source: {type: header, header_name: X-Tenant-Id}
  bypass_roles: [admin]
```

expecting an "admin can see across every tenant" pattern (very common for a
real multi-tenant SaaS - a platform operator needs global visibility).
`backstudio validate` rejected this immediately and correctly, per
`app/erd/loader.py`'s own validation message:

> `rls.bypass_roles` has no effect when `identity_source.type` is `'header'`
> — the header identity source resolves ownership purely from the request
> header and never reads any role information, so there is nothing for a
> bypass role to plug into.

This is intentional and the error message explains the mechanical reason
clearly - but it means **there is currently no way to express "platform
admin sees every tenant" when using header-based multi-tenancy**, which is
a very common real-world requirement for exactly the kind of app this
identity source exists for. An admin using this generated API would need
to already know and supply the specific tenant's own header value per
request (i.e., admin isn't actually "global," just another header-scoped
caller) - or the header-resolution logic itself would need a documented,
deliberate carve-out (e.g., "if caller has an RLS-bypass role and doesn't
supply the header, don't filter at all") that doesn't exist today.

I worked around this in the final example by simply not attempting an
admin-bypass on `Project`/`Task` — `admin` and `member` are functionally
identical on those two entities' RLS behavior; `admin`'s only distinguishing
power in that example is managing the `Tenant` registry itself (RBAC-gated,
unrelated to RLS). Worth a decision on whether this is a real gap to close.

## 4. Documentation gap: module routes are NOT prefixed by module/service name

**Severity: cost me real debugging time; not a bug, but genuinely
under-documented.**

I assumed - by analogy with the auth module's own `/auth` prefix
(`app.include_router(auth_router, prefix="/auth", ...)` in `server.py.jinja`)
- that a `services:` entry named `catalog` with entities `[Category, Tag,
Product]` would generate routes under `/catalog/categories`,
`/catalog/products`, etc. It does not. Every module's router is mounted with
**no prefix at all**:

```python
app.include_router(catalog_router)
app.include_router(ordering_router)
app.include_router(reviews_router)
app.include_router(auth_router, prefix="/auth", tags=["auth"])
```

so the real routes are bare `/categories`, `/products`, `/orders`,
`/order_items`, `/reviews` - directly at the API root, with **only** the
auth module getting a prefix. I hit real 404s writing my first test pass
because of this assumption and had to read the generated `routes.py` files
directly to find the actual paths.

I checked `docs-site/erd-reference/fields.md` and `docs-site/architecture/templates.md`
for this - the only related mention is `endpoints.base_path`
("Overrides the generated route prefix"), which documents how to **override**
a route's prefix per-entity but never states what the **default** (no
`base_path` set) actually is. Nothing in the docs states that module/service
names do NOT become URL prefixes. This is worth adding explicitly to either
the ERD reference (`endpoints.base_path`'s row) or the CLI/architecture docs
— a new user modeling multiple services and expecting namespaced URLs (a
very natural assumption, and the one I made) will hit the same friction I
did.

## Positive finding: cross-user ownership-cascade writes are correctly rejected

Not an issue - noting this because I specifically tried to break it and
couldn't. In `personal_finance.yml`, `Transaction` doesn't declare its own
RLS (`owner: true`) - it inherits ownership from `Account` via
`cascades_ownership: true`. I tested whether a non-owning user could create
a `Transaction` by supplying a *different* user's real `account_id` (i.e.,
attempting to attach a hostile transaction to someone else's account by ID):

```
member creating Transaction against admin's account_id
-> 400 {"detail": "Account 1 not found"}
```

The FK-existence check for `account_id` is itself RLS-filtered, so from the
non-owning caller's perspective the referenced account genuinely doesn't
exist - the cascade can't be defeated by supplying a foreign row's real ID.
Good, correct behavior; no action needed, just confirming it holds under a
real, adversarial-shaped test rather than assuming it from reading the code.

## What was tested, and how

All three new examples (`ecommerce.yml` / **ShopSphere**, `multi_tenant_saas.yml`
/ **TaskFlow**, `personal_finance.yml` / **LedgerBox**), plus the existing
`blog.yml` / **BlogAPI** for reference, are generated into `workspace/` and
kept there (not deleted) alongside their HTML ER diagrams
(`workspace/{name}-diagram.html`, via `backstudio visualize`).

Each of the three new ones was exercised with a real HTTP-shaped round trip
against the actual generated FastAPI app (via Starlette's `TestClient`
against a real SQLite database on disk — the same technique this repo's own
`test_generated_project_runtime.py` uses, not a mock):

- **ShopSphere** (`email_verification` mode, sync): register → login before
  verify (401) → capture the real verification token from the dev-mode
  email-stub's stdout → verify → login (200) → create Category/Tag/Product
  (confirming the many-to-many `tag_ids` field is present but correctly
  read-only on create, a documented pre-existing limitation, not new) →
  create Order/OrderItem (the association-object many-to-many-with-extra-fields
  pattern) → create Review → list Products.
- **TaskFlow** (`open` mode, async, header-scoped RLS): register (bootstrap
  gets every role, no approval/verification gate under `open` mode) → login
  → create two Tenants → create a Project under one tenant's `X-Tenant-Id`
  header (confirming the owning FK is auto-stamped from the header, not
  client-suppliable) → create a Task under it → confirm the *other* tenant's
  header sees **zero** of the first tenant's projects (real isolation, not
  just "it didn't error") → confirm a request with no `X-Tenant-Id` header
  at all fails with a clean `422` rather than something worse.
- **LedgerBox** (`admin_approval` mode, sync, `auth_user`-scoped RLS with
  ownership cascade): register bootstrap admin (confirmed auto-approved,
  the admin-approval-bootstrap fix from an earlier session holds) → create
  an Account + Transaction as admin → register a second, non-bootstrap user
  (confirmed **not** auto-approved, and confirmed login is refused until
  approved) → admin approves them → confirmed the newly-approved user still
  has **zero roles** until the admin explicitly grants `member` (the
  established, documented role-bootstrap behavior) → member creates their
  own Account/Transaction → confirmed a member only ever sees their own
  Account in a list, and a direct `GET` of admin's Account 404s for them →
  confirmed admin (holding the RLS `bypass_roles`) sees both accounts → the
  adversarial cross-user-cascade-write test from the "Positive finding"
  section above.

All three passed every assertion on the final run (after fixing the test
script itself for the two non-bugs described above — reserved-TLD email
addresses in my own test data, and the unprefixed-route-path assumption from
finding #4). Every generated project was also individually verified to
byte-compile cleanly (`python -m compileall`) before the HTTP testing began.
